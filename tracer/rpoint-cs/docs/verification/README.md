# docs/verification/

## Goal

Audits of **completed capture campaigns** — what was actually run, what the
resulting traces actually measured, and where the methodology failed silently.
These are written after the fact, about a campaign that is already finished.

## Not to be confused with `docs/validation/`

The two names are close and the distinction is load-bearing:

| | asks | run | subject |
|---|---|---|---|
| **`validation/`** | *Is **this trace** healthy?* | every capture, before trusting it | one artifact |
| **`verification/`** | *Was **this methodology** sound?* | once per campaign, afterwards | the whole approach |

`validation/` catches a broken tracer. **`verification/` catches a working
tracer pointed at the wrong thing** — which is the failure mode that has actually
cost this project a campaign, because every mechanical gate passes while the
result is unusable.

## How this fits into the repo

Read the relevant audit **before** re-running a workload's playbook in
`docs/workloads/`. The playbooks describe the intended procedure; the audits
record where that procedure produced a result nobody wanted, and the parameters
that were in force when it did. Where the two disagree, the audit is the
observation and the playbook is the intent.

An audit is a dated snapshot, never edited into agreement with later work. If a
finding is superseded, add a new audit and link back — do not rewrite history in
place, because the value of these documents is that they record what was believed
at the time.

## Reading a finding

Every audit grades its findings **A (verified) / B (computed) / C (deduced) /
D (modelled)** in a table near the top, and states the model and date that
produced it. Grade C and D claims are reconstructions and forecasts. Do not carry
one into a paper, a commit message, or another agent's prompt without
re-verifying it first — each one names the check that would settle it.

## Files

### `2026-09-04-memcached-rocksdb-capture-audit.md`

Audit of the first Memcached (QEMU/TCG) and RocksDB (PIN) campaigns, whose traces
turned out not to exercise the memory system. Generated by Claude Opus 5 (1M
context) across two multi-agent passes, the second including an adversarial
refutation round that changed the conclusion.

The load-bearing findings:

- **The Memcached client and store never shared a keyspace.** YCSB wrote
  `usertable-user<fnv64>`; memtier read `memtier-<N>` because `--key-prefix` was
  never passed. Every mechanical gate passed anyway.
- **The Zipfian exponent was never chosen** — `--key-zipf-exp` is absent
  everywhere, and memtier defaults it to 1.0.
- **The documented dataset size is wrong** in four places; the real load evicted
  ~366 K items against a checklist that requires zero.
- **RocksDB's committed spec describes a configuration nobody ran**, and its own
  success criterion targeted a cache-resident workload.
- **`trace_sanity_check` cannot detect either defect** — reproduced on
  purpose-built traces; it ignores stores, has no line granularity, and has no
  skew metric at all.
- Corrections to several things this project believed: the published Zipf α band
  for KV caches, the usability of ChampSim's DRAM bandwidth histogram as a
  criterion, and the weakness of database size as a lever on in-window footprint.
- A flag-trap list for `memtier_benchmark` and `memcached`, all read in source,
  every one of which fails silently.
